# 写真・音声の保存回帰テスト

## 実行

ワークスペースで Node.js 24、pnpm、Java 21 以上を使用します。
依存関係は `pnpm install --frozen-lockfile` で導入できます。
このReplitではJavaを `.replit` のNixパッケージとして設定しています。

```sh
pnpm --filter @workspace/kids-voice-encyclopedia run test
pnpm --filter @workspace/kids-voice-encyclopedia run test:cloud
pnpm --filter @workspace/kids-voice-encyclopedia run typecheck
```

`test:cloud` はFirestoreとStorage Emulatorを起動し、テスト終了時に停止します。
初回はFirebase CLIがエミュレーターのJARをダウンロードします。
ポート8087、9197、4400、4500、9150が空いている必要があります。
権限拒否を検証するため、テスト中の `PERMISSION_DENIED` は想定内です。
判定はコマンドの終了コードとテストの集計で確認してください。

## 実データを触らない仕組み

- プロジェクトを `demo-keepsakes-test` に固定し、両エミュレーターを127.0.0.1に接続します。
- テスト側でもプロジェクトIDと両接続先を検査し、不一致ならクライアント作成前に失敗します。
- 実アプリの `firebaseConfig.ts` はインポートせず、資格情報や `GOOGLE_API_KEY` は子プロセスに渡しません。
- テストごとの消去は、このローカルのdemoプロジェクトのみで行います。
- 写真は1ピクセルPNG、音声はメモリ上で生成した無音WAVです。家族のファイルは読みません。
- 本番のバケット診断プローブはテスト時には無効です。
- ルール公開、Cloud IAM、課金設定、本番データの変更は行いません。

## 検証内容

本番と同じ `createKeepsakeRepository` を、Firebase SDKと実際のルールが動くエミュレーターに接続します。
写真・音声のアップロード、URLとパスのFirestore保存、新しいクライアントでの購読、
写真の取得と再生用音声URLの取得・WAVバイト確認、カードと両ファイルの削除を検証します。
ブラウザのマイク録音やスピーカーからの実音再生を確認するテストではありません。

成功するSDK操作は実エミュレーターで実行します。失敗系はその境界で障害を注入します。
初回アップロード失敗、写真成功後の音声失敗、URL取得失敗、実ルールによるFirestore拒否、
結果確認中の切断、確定後の応答喪失、タイムアウト後の遅延確定、
同じ画面の二重保存と別セッションの同時保存、削除の部分失敗・再試行を含みます。
障害注入は再現可能な通信エラーのシミュレーションであり、実ネットワークの物理切断ではありません。

別UIDと未認証のクライアントによるFirestore読み取り・一覧取得・更新・削除、
Storageのバイト取得・メタデータ取得・URL取得・上書き・削除が拒否されることを検証します。
旧形式の保存パス、写真のみのカード、移行の再試行、不正形式・空・20MB以上の入力も検証します。

### エミュレーターとの形式差

NodeのFirebase Storage SDKにはBlobの代わりに同じバイト列をUint8Arrayで渡します。
エミュレーターのダウンロードURLはHTTPのため、テストのアダプターだけでホストを
本番形式の `https://firebasestorage.googleapis.com` に変換してFirestoreへ保存します。
バケット名・オブジェクトパス・トークンはSDKの実際の戻り値を保持し、
取得・削除時にはローカルホストへ戻します。本番ルールにlocalhostの例外は追加しません。

### アクセス検証の範囲

Firebaseのダウンロードトークン付きURLは、URLを知る人が認証なしでも使用できる仕組みです。
このテストは別UIDによる認証付きAPIアクセスとURL取得の拒否を確認しますが、
流出したトークンURLからの閲覧拒否を保証しません。URLをログ・共有画面などへ公開しないでください。
URL流出時にも認証を必須にするには、トークンURLではなく認証付きメディア取得への変更が必要です。

## 新しい保存パスとルール

新規ファイルは `users/{uid}/keepsakes/{id}/{保存試行ID}/photo` と `voice` に保存します。
独立した保存試行で既存ファイルを上書き・削除しないための形式です。
Firestoreトランザクションで同じカードIDの最初の保存だけを採用し、
同時保存で負けた試行のファイルだけを片付けます。保存済みIDの再実行は編集ではありません。
応答が失われて確定結果が不明な場合は、安全のためファイルを保持します。
未使用ファイルを自動で一括削除する仕組みは含めていません。

**公開環境でこのアプリ変更を使う前に、更新したFirestoreと対象バケットのStorageルールを先に公開してください。**
公開手順は `STORAGE_TROUBLESHOOTING.md` を参照してください。
旧形式の `.../{id}/photo` と `voice` は引き続き読めて削除できます。
既存カードや既存ファイルの移行・削除は不要です。

## 未使用ファイルの確認・個別削除

一覧の「保護者向け：未使用ファイルの確認」から開きます。開いただけでは走査も
削除も行いません。「読み取り専用で一覧を確認」で、現在設定しているバケット内の
この匿名認証UIDのファイルを一覧にします。別利用者・旧バケットは走査しません。
確認時刻、パス、サイズ、更新時刻、保持理由を表示し、写真・声の内容やトークンURLは表示しません。
Firestoreの参照一覧と保存試行状態は `getDocsFromServer` で読みます。
読めない場合や解釈できない古いURLがある場合は、一覧全体を失敗として削除を禁止します。

### 保持の判断

- カードの写真・声パスとURLの両方を検査します。旧URLにしか参照がないカードも保護します。
  旧バケットの同じパスも保守的に保護し、1ファイルでも参照された試行は丸ごと保護します。
- 新しい保存は、アップロード前に `saveAttempts` に `active` を記録し、
  カードの確定と同じFirestoreトランザクション内で `finished` にします。
  同時保存で採用されなかった試行も確定処理の終了を記録します。
- `active`（保存中・結果不明）は経過日数にかかわらず削除不可です。
  タイムアウトしても、遅延確定が終わるまでは保持します。時間だけでは完了とみなしません。
- 旧形式のパス・試行状態の記録がないファイルも閲覧のみです。既存のファイルに完了状態を
  推測して付けたり、旧バケットへ切り替えて削除したりしません。
- 未参照の `finished` / `blocked` の試行で、終了時刻とStorage更新時刻の両方から
  **7日以上**経過したファイルだけを削除候補にします。
  Firestoreルールもサーバーの `request.time` で終了から7日間を強制します。
  端末の時刻が進んでいても、このサーバー側待機期間を短縮できません。

### 削除の操作と競合対策

候補ごとの「このファイルの削除を確認」でパスを確認し、
「この1ファイルを削除する」で明示的に確定します。削除は元に戻せません。
全選択・一括削除・定期削除・バックグラウンドの削除再試行はありません。

削除直前にサーバーの参照一覧とStorageメタデータ・世代を再確認します。
対象カードと試行状態をFirestoreトランザクションで読み、
参照がないこと・完了済みであること・待機期間終了を再検証し、
試行を永久的に `blocked` にします。ルールでも参照中の試行のブロックを拒否します。
ブロックされた試行を使うカードの作成・メディア更新は拒否されるため、
削除確認と遅延コミットが競合しても削除済みファイルを指すカードを確定できません。
カードのURLとパスを一致させるルールも設け、別カードのURLでブロックを迂回させません。
ブロック記録の消去・再活性化は許可しません。カテゴリ・名前だけの編集には影響しません。

最後にサーバー参照をもう一度確認してから、選んだ1ファイルだけを削除します。
通信失敗や部分失敗ではブロック記録を残し、一覧を再確認して再度明示的に承認するまで
再試行しません。兄弟の写真・音声をまとめて削除することもありません。
管理者権限によるルールを迂回する書き込みや手動上書きは、この操作と同時に行わないでください。

### 公開前に必要なこと

この変更はルールを自動公開しません。実環境のファイルにも変更を加えていません。
新しい保存は試行状態を書き込むため、**アプリ公開前に更新した `firestore.rules` と、
現在使用するバケットの `storage.rules` を公開する必要があります**。
ルール未公開の状態で新しい保存や確認を行うと、権限エラーとなり安全側で中断します。
旧バケットの削除や既存カードの再保存は必要ありません。

### 回帰テスト

`test:cloud` は参照中、旧形式、旧バケットのURLのみの参照、結果不明の試行、
タイムアウト後の遅延確定、同時保存、最近更新されたファイル、完了から7日未満、
サーバー読み取り失敗、走査後の参照追加と確定直前の競合、世代変更、
個別承認なしの拒否、削除の部分失敗と明示的再試行、ブロックの永久性、
別UID/未認証の一覧取得拒否、不明URLでの削除停止を検証します。

Storageの更新時刻はWeb SDKでは過去へ変更できないため、テスト用アダプターだけで
更新時刻に8日前相当の時間経過を模擬します。実際のパス・バケット・世代・バイトは
エミュレーターのものを使います。Firestoreの過去の終了時刻はdemoプロジェクトの
エミュレーター専用管理コンテキストで投入し、サーバー側の7日間ルールも検証します。
試験ごとに**指定demoバケットの階層を再帰的に消去**してから実行します。
`rules-unit-testing` の `clearStorage()` は既定バケット直下のファイルしか消さないため、
階層化した保存パスの試験にはそれだけを使いません。

UIの合成データ専用ページは、開発サーバーの `/tests/unused-media-preview.html` です。
本番ビルドのエントリではなく、Firebase設定・Store・認証・クラウド操作を読み込まず、
実際のダイアログにメモリ上のサービスを注入します。
確認・取消・1件削除・二重クリック防止・エラー時の停止・小画面でのスクロールを、
実際の家族データにアクセスせず確認できます。
`?inspected=1` は初回一覧表示、`?failure=scan` と `?failure=delete` は失敗の表示です。
